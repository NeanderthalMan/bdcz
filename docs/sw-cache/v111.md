# v111 — the shell's scripts come from the cache first (bc-iaju1.6)

## What changed

`public/sw.js` gained a branch above network-first: a request for one of the shell's own
`.js`, `.css` or `.svg` files is answered out of the cache and revalidated behind the
screen. Documents are untouched and stay network-first. It also gained a `message`
handler, `beadcause:sw-refresh`, which re-fetches the whole of `SHELL` in one `addAll`
and answers the page that asked.

`public/update.js` sends that message, and waits up to two seconds for it, in the moment
between `registration.update()` and `location.reload()`.

`public/index.html` and `lib/server.js` changed in the same branch — seven of the panes'
scripts are injected after the first paint rather than parsed at boot (the new
`public/panelazy.js`, which is in `SHELL`), and the static handler now answers `304` and
sends gzip.

## Which two files must not be mixed

**`update.js` and `sw.js`.** This is the pair that owes the bump. `update.js` now posts a
message that only a worker from this version answers, and it is posted on the one path
that matters — the reload after a deploy. A phone holding the new `update.js` against the
old worker would post into silence, wait out its two seconds and reload anyway, so that
direction degrades rather than breaks; the other direction is what this version prevents
outright.

**`index.html` and the pane scripts.** The page no longer carries `<script src>` tags for
`history.js`, `releases.js`, `config.js`, `montabs.js`, `monitor.js`, `prs.js` and
`mirror.js`; it carries `panelazy.js`, which injects them after the first paint. A cached
`index.html` from before this version served against a worker from after it would be a
page that loads those seven twice — the tags *and* the injected copies — and several of
them register a pane builder as they run. That is the mixed pair in its clearest form.

**`panestage.js` and `panelazy.js`.** The staged boot now asks the loader whether the
landed-on pane's script is still in flight, and waits once if it is, so a deep link to
`/#history` still builds the ledger before the inbox. It asks with `?.`, so a page with
the old `panestage.js` and the new loader boots the way it always did — one load where a
deep-linked pane is built second. The other direction needs no defence: the new
`panestage.js` against no loader at all is the same optional call.

## The argument for cache-first, and what stands behind it

bc-iaju1.6 measured a cold open at 2.24 MB, of which 2.19 MB is scripts and stylesheet.
The same commit gave `lib/server.js` an ETag, so those bytes are no longer *sent* on a
warm load — but the 34 conditional requests still are, and over a tailnet, on a phone that
has just woken up to a notification, those round trips are the wait.

Serving them from the cache means a phone can be one generation behind the daemon for one
load. Three things bound that, and two of them already existed:

- The version at the top of `sw.js`. A change that leaves a *broken* pair owes a bump, and
  a bump is one atomic `addAll` of the whole list — which is exactly the discipline this
  note is part of.
- `update.js` reloads after any deploy that moved `public/`, and it already went through
  `registration.update()` and waited for `controllerchange` before doing so. Its own
  comment said why: "or the shell cache hands the same files straight back". It was
  written for this.
- And now the refresh message, which closes the remaining case: a deploy that moved
  `public/` additively and legitimately owed no bump. Without it that reload would come
  back on the files it left.

## Why documents are not in it

The sign-in gate in `lib/server.js` intercepts `rel.endsWith('.html')` and deliberately
leaves every asset open. So a `.js` answered from this cache cannot be a login page
arriving where a script was expected — a request for it was never going to be answered
with one. A *document* answered from the cache is exactly that failure: a signed-out
browser given the shell, with no data, and no account of why. The line is drawn on the
extension rather than on `request.mode`, because a `/graph.html` pulled into a drawer is
fetched as a sub-resource and the gate applies to it just the same.
